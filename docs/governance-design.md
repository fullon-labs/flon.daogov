# HuFu 治理中心 DApp 设计

> 本文描述拟在 HuFu App 内提供的 FullOn 治理中心。它是目标产品与实施方案，不代表相关链上合约和页面已经全部上线。

## 1. 产品定位

治理中心把两类相关但权限不同的治理统一到一个入口：

1. **网络治理**：BP 候选人注册、节点排名、选民质押 FLON、获得 GLON、选择或调整 BP、领取投票奖励。
2. **DAO 治理**：创建提案、社区附议、正式投票、等待执行、链上执行和结果审计。

统一入口不等于合并合约。网络治理由 `flon.system`、`voter.reward` 和 `flon.token` 承担；DAO 治理由独立治理合约承担。前端只负责读取、解释、构造交易和调用 HuFu 钱包签名，不能代替链上判断结果。

### 设计原则

- 使用 **Block Producer（BP）**，不使用含义模糊的“超级节点”。
- 所有影响资产、票权或执行权限的动作都由 HuFu 钱包明确展示后签名。
- 排名、票权、奖励、提案状态和执行结果以链上状态为准；索引服务只加速查询。
- GLON 是不可转让的治理凭证，不是可交易资产，也不承诺固定收益。
- 节点投票和 DAO 投票共享治理身份与 GLON 展示，但不能默认为同一次授权或同一套快照。
- 每个关键状态展示生效 epoch、截止时间、区块号和交易 ID，避免“已提交”与“已生效”混淆。

## 2. HuFu 内的入口与形态

### 推荐形态

以现有 Flutter `hufu-daogov-module` 为基础升级为 HuFu 原生插件，而不是另做一个持有私钥的网页。

- 首页“推荐 DApp”增加 **治理中心**。
- 发现 > FullOn 增加 **治理中心**固定入口。
- 我的 > DApp 管理展示最近使用、待处理签名与治理通知。
- DApp 页面通过现有事件总线请求当前网络、账户和 FLON 交易签名。
- 私钥始终留在 HuFu 钱包；治理模块只接收签名结果和交易状态。

如未来同时提供 H5 版本，H5 只能通过 HuFu DApp Bridge 或标准钱包连接协议请求签名，不能读取或保存私钥。

### 一级页面

```text
治理中心
├── 概览
├── BP 竞选
├── 节点投票
├── DAO 治理
└── 我的治理
```

顶部始终展示：

- 当前网络：测试网或主网，使用明显不同的颜色和标签
- 当前账户名和本地钱包昵称
- FLON 可用余额、已投票 FLON、GLON 余额
- 待领取奖励
- 网络同步状态和数据对应区块高度

## 3. 治理中心概览

概览不是简单数据大屏，而是用户的任务入口。

| 区域 | 内容 | 主要动作 |
| --- | --- | --- |
| 我的治理权 | FLON、已质押 FLON、GLON、当前选择的 BP 数量 | 增加投票、调整节点、撤票 |
| 网络状态 | Active BP 数量、30 个 Standby、当前 epoch、下次换届时间 | 查看完整排名 |
| 奖励 | 已结算、待结算、最近结算 epoch | 领取奖励、查看明细 |
| 治理任务 | 待附议、投票中、待执行、我发起的提案 | 继续处理 |
| 风险提示 | 待生效票权、节点离线、提案即将截止、错误网络 | 查看详情 |

当早期 Active BP quorum 小于 21 时，页面同时显示：

- 当前启用席位，例如 `3 / 21`
- Standby 仍为 `30`
- 奖励使用固定目标席位预算或治理参数限制，不把 21 份预算全部平均给 3 个 BP

## 4. BP 竞选

### 4.1 候选人列表

候选人列表分为三个区域：

- **Active BP**：当前实际出块席位，最终上限 21。
- **Standby BP**：固定展示排名靠前的 30 个备用节点。
- **其他候选人**：已注册但未进入 Active 或 Standby 的节点。

每张节点卡展示：

- BP 链上账户名和显示名称
- Active / Standby / Candidate / Suspended 状态
- 总有效票权、排名、距上一名或安全线的票权差
- 自质押、投票人数、承诺给选民的奖励分享比例
- 最近 24 小时和 7 天在线率/出块率
- 最近一次出块、漏块次数、处罚或冷却状态
- 注册网站、X 账号、节点地区、API/状态页
- 注册信息更新时间和验证状态

网站、X 账号和介绍可使用链下元数据 URI，但链上保存其 URI 与内容哈希。界面要区分“候选人声明”和“平台/社区已验证”。

### 4.2 竞选申请

申请分为四步：

1. **资格检查**：账户、最低自质押、GLON/FLON 条件、未处于处罚期。
2. **节点信息**：显示名称、网站、X、地区、技术联系人、状态页、隐私政策。
3. **技术信息**：BP 公钥或 authority、P2P/API 地址、监控证明。
4. **确认签名**：完整展示链、账户、自质押、奖励分享比例和注册 action。

对应现有网络合约能力：

- `flon.system::regproducer` 或 `regproducer2`
- `flon.system::unregprod`
- `flon.system::claimrewards`

当前 `regproducer` 只有 `url` 和 `location` 等有限字段。网站、X、状态页等结构化资料需要新增 BP registry 合约/表，或将版本化 JSON 放入内容寻址存储并把 URI 与哈希写链。不要把未经验证的远程 JSON 当成链上事实。

### 4.3 在线率与处罚展示

在线率不能由 App 自报。建议显示两组指标：

- **链上确定性指标**：排班块数、实际出块数、连续漏块、被暂停的 epoch，由 `onblock` 和排班数据计算。
- **链下可用性指标**：API、P2P、状态页探测，仅作为运维参考，不直接触发本金罚没。

普通下线采用奖励扣减、失去资格、冷却期和 Standby 自动递补；双签或冲突状态等可验证作恶才进入更严厉的 slash 流程。

## 5. 节点投票

### 5.1 投票模型

- 用户用 FLON 增加投票本金，链上生成等额 GLON。
- 一份总票权最多选择 30 个 BP，权重在所选 BP 之间平均分配。
- 例如 300 GLON 选择 3 个 BP，每个 BP 获得 100 有效票权；选择 30 个时每个获得 10，不能把 300 复制成 9,000。
- 用户可随时修改 BP 列表；新分配从下一 epoch 生效。
- `subvote` 时对应 GLON立即交回 issuer 并销毁/retire，不能继续参与新 DAO 提案；BP 排名和奖励票权在下一个 epoch 边界移除。
- 六小时为一个奖励 epoch。页面必须分别显示“当前配置”和“下个 epoch 生效配置”。

### 5.2 投票页面

```text
┌ 当前票权 ─────────────────┐
│ 1,200 GLON   已选 6 / 30   │
│ 本 epoch：每节点 200        │
│ 待生效：每节点 171.428...   │
└───────────────────────────┘

[搜索] [Active] [Standby] [全部] [仅高在线率]

☑ bp.alpha   #2  Active   99.98%   分享 30%
☑ bp.beta    #9  Active   99.91%   分享 45%
☐ bp.gamma  #23  Standby  99.99%   分享 50%

[调整投票本金]                  [确认节点分配]
```

排序默认采用综合信息而不是仅按票数，允许用户切换：排名、在线率、分享比例、投票人数、地区。UI 不应把收益率作为唯一推荐依据。

### 5.3 三类独立交易

| 用户目的 | 链上动作 | 生效说明 |
| --- | --- | --- |
| 增加本金 | `flon.system::addvote(voter, vote_staked)` | FLON 锁定、GLON生成；排名/奖励权重下一 epoch 生效 |
| 调整节点 | `flon.system::voteproducer(voter, producers[])` | 不改变本金；新分配下一 epoch 生效 |
| 撤回本金 | `flon.system::subvote(voter, vote_staked)` | GLON立即退出治理；排名/奖励权重下一 epoch 移除，FLON按退款规则返回 |

如果用户一次同时增加本金并选择节点，HuFu 可以构造一笔含多个 action 的原子交易；签名页仍需逐项展示含义。

### 5.4 奖励

奖励页分开显示：

- **BP 奖励**：仅 BP 调用 `flon.system::claimrewards` 提取已结算的生产者奖励。
- **投票人奖励**：由 BP 奖励分享在 epoch 结算后进入 `voter.reward`，用户调用 `voter.reward::claimrewards` 领取。
- **待结算奖励**：只能作为估算，并标注尚未成为可领取余额。

每条明细包含 epoch、历史有效票权、所选 BP、各 BP 分享金额、总额、结算交易和领取交易。不能用当前票权倒推历史奖励。

## 6. DAO 治理

### 6.1 GLON 在 DAO 中的角色

GLON 表示锁定 FLON 所形成的治理权。DAO 合约应读取确定性快照，而不是直接读取用户点击投票时的实时余额。

建议规则：

- 提案进入正式投票时记录 `snapshot_epoch` 或快照根。
- 只有快照时已生效的 GLON 参与该提案。
- 快照后新增 GLON不能参与当前提案，避免临界时刻买票。
- `subvote` 立即销毁 GLON后，用户不能参与新提案；对已经投出的历史选票是否保留，由合约在提案创建时固定规则，不能由前端决定。
- GLON禁止用户间转账；否则节点投票本金所有权、赎回权和 DAO 票权会分离。

### 6.2 提案生命周期

```text
草稿 Draft
  └─提交─> 附议期 Endorsement
             ├─未达门槛─> 未立案 Rejected
             └─达到门槛─> 投票准备 Pending Vote
                              └─快照─> 投票中 Voting
                                          ├─未达 quorum / 未通过─> Defeated
                                          └─通过─> Timelock
                                                      ├─挑战/安全否决─> Cancelled
                                                      └─到期─> Executable
                                                                  ├─执行成功─> Executed
                                                                  └─执行失败─> Execution Failed / Retryable
```

“附议”与“正式投票”必须是两个阶段：

- 附议只决定议题是否值得占用正式治理资源。
- 正式投票决定提案是否通过。
- 附议票不自动继承为赞成票，进入正式投票后需要重新确认。

### 6.3 提案类型

| 类型 | 示例 | 执行方式 |
| --- | --- | --- |
| 文本/信号提案 | 社区方向、非绑定意见 | 记录结果，不自动执行资产或权限动作 |
| 参数提案 | Active BP quorum、奖励比例、处罚阈值 | Timelock 后调用白名单 action |
| 资金提案 | 使用 `flon.gas` 的纯锁定余额或 DAO treasury | 限额、收款方、币种、预算周期均写入 action |
| 合约升级提案 | 升级系统或治理合约 | 高门槛、多签/安全委员会复核、长 Timelock |
| 紧急提案 | 暂停高风险 action | 仅限预定义暂停能力，不允许借紧急流程任意转账 |

### 6.4 创建提案

创建器采用向导：

1. 选择提案类型。
2. 填写标题、摘要、动机、规格、风险、预算和验收标准。
3. 对执行型提案选择白名单合约与 action，由 ABI 表单构造参数。
4. 模拟执行，展示权限、资金变化和失败原因。
5. 展示发起门槛、附议门槛、投票期、quorum、通过阈值和 Timelock。
6. 上传正文，链上记录内容哈希和 URI。
7. 钱包签名提交。

执行型提案禁止用户直接输入不可解释的十六进制 payload 后盲签。高级模式可以显示 packed data，但必须同时展示 ABI 解码结果。

### 6.5 提案详情

详情页采用一条可审计时间线：

- 当前阶段、倒计时、创建区块和快照 epoch
- 提案人、正文哈希、版本和附件
- 附议人数/权重与门槛
- 赞成、反对、弃权、quorum 和通过阈值
- 我的快照票权、是否已投、交易 ID
- 将要执行的合约、action、参数和资产变化
- Timelock 开始/结束时间
- 执行交易、返回状态和失败原因

按钮只显示当前可执行动作：`附议`、`投票`、`取消草稿`、`执行`、`重试执行`。阶段已结束时不显示误导性的可点击按钮。

## 7. 治理合约 V2 要求

现有 mDAO 与 Flutter 模块可复用 DAO、策略、提案列表和钱包签名基础，但当前代码接口存在版本差异：Flutter 层包含 `startvote`、`execute`、`addplan` 和 `setaction` 调用，而已检查的 `mdao.propose` 主要提供 `create`、`votefor`、`cancel`。上线前必须统一 ABI，不能只补 UI。

建议在兼容现有数据的前提下增加或重构以下 action：

| Action | 作用 |
| --- | --- |
| `createprop` | 创建草稿，保存正文 URI/hash、类型和执行计划 |
| `submitprop` | 进入附议期并冻结提案版本 |
| `endorse` | 按快照前置规则附议，一账户一条记录 |
| `startvote` | 达门槛后创建 GLON 快照并进入正式投票 |
| `castvote` | 赞成、反对或弃权；是否允许改票必须由参数固定 |
| `finalize` | 截止后确定 quorum 与结果，进入 Timelock 或失败状态 |
| `execute` | Timelock 到期后执行白名单 action；任何账户均可触发 |
| `cancelprop` | 仅在规则允许的阶段取消，并记录原因 |
| `veto` | 可选的受限安全否决，只能在 Timelock 内使用并完全留痕 |

必须新增：

- 提案版本冻结与正文哈希
- 附议记录和防重复
- GLON 快照/历史票权读取
- `proposal_id + voter` 唯一投票记录
- quorum、通过率和 Timelock 的提案级快照
- action 白名单、资产限额和目标账户限制
- 执行幂等状态，防止重复执行
- 失败可重试与不可重试错误区分
- 合约迁移和旧提案只读兼容方案

```text
HuFu App
├── 治理中心 Flutter UI
├── Governance Repository
│   ├── FLON RPC Reader
│   ├── Index API Client
│   └── Local pending transaction cache
├── Transaction Builder

        │
        ├── flon.system      BP 注册、节点投票、BP 奖励、epoch
        ├── voter.reward     投票人历史票权与奖励
        ├── flon.token       FLON 与不可转让 GLON
        ├── bp.registry      BP 扩展资料（建议新增）

├── 节点排名、历史在线率和 epoch 聚合

```

### 数据职责

| 数据 | 权威来源 | 索引服务职责 |
| --- | --- | --- |
| FLON/GLON 余额 | 链上 token tables | 聚合展示，不得覆盖链上值 |
| 当前与待生效节点选择 | `flon.system` / `voter.reward` tables | 快速查询和历史展示 |
| BP 排名与奖励 | 链上 tables + epoch 记录 | 统计、分页、曲线 |
| 在线率 | 链上出块统计 | 按 24h/7d 聚合 |
| 提案状态和票数 | DAO 合约 | 搜索、排序、通知 |
| 提案正文 | 内容存储 + 链上 hash | 缓存并校验 hash |
| 用户本地昵称 | HuFu 本地安全存储 | 不上传 |

## 9. 钱包签名体验

每次签名前固定展示：

- 网络和 chain ID
- 发起账户与 permission
- 合约、action 和人类可读说明
- FLON/GLON 数量变化
- 节点列表或提案 ID
- 当前 epoch、预计生效 epoch或快照 epoch
- 费用/资源消耗
- 风险提示与不可逆结果

交易状态统一为：

`待签名 → 已签名 → 已广播 → 已入块 → 不可逆 → 业务生效`

“已入块”不一定等于“投票已计入排名”；节点投票要继续显示“将在 Epoch N 生效”。交易失败时保留原表单，但不能自动重复签名或重复广播。

## 10. 通知

默认只推送需要用户行动或显著状态变化的事件：

- 节点投票将在下一 epoch 生效
- 所投 BP 进入暂停/冷却或掉出 Standby
- 奖励已结算可领取
- 提案进入附议、正式投票或最后 24 小时
- 提案通过并进入 Timelock
- 提案可执行、已执行或执行失败

通知点击后打开对应详情，不直接触发签名。

## 11. 安全与治理护栏

- 主网和测试网视觉隔离，主网签名页再次确认。
- 所有执行型提案先 ABI 解码和本地模拟。
- 治理合约只可执行白名单目标/action；升级白名单本身也必须走高门槛治理。
- 资金提案使用单笔、周期和总预算上限。
- 合约升级、权限修改和大额资金设置更高 quorum、更高通过率和更长 Timelock。
- 索引服务故障时，用户仍可读取关键链上状态并签名；无法确认数据完整性时禁止展示“可执行”。
- 远程 BP 资料、提案正文和图片均按不可信内容处理，防止恶意链接和签名诱导。
- Aime 可以解释提案和模拟影响，但不能代替用户选择、签名、投票或执行。

## 12. MVP 与实施顺序

### Phase 1：只读治理中心

- 概览、Active/Standby/Candidate 列表
- BP 详情、排名、链上在线率
- 我的 FLON/GLON、当前/待生效投票、奖励明细
- DAO 提案列表和详情

### Phase 2：节点交易闭环

- BP 注册/更新/退出
- `addvote`、`voteproducer`、`subvote`
- 投票人奖励领取、BP 奖励领取
- 钱包签名、交易状态和 epoch 生效提示

## 13. 验收标准

- 用户可在 HuFu 内完成 BP 注册、加票、换票、撤票和奖励领取，不接触私钥。
- UI 能同时正确展示当前票权和下个 epoch 待生效票权。
- 选择 1–30 个 BP 时，总有效票权守恒，不因选择数量放大。
- `subvote` 后 GLON立即退出可用于新提案的余额。
- 奖励明细使用奖励产生期间的历史票权，不使用领取时的当前票权。
- 提案能完整经历草稿、附议、投票、Timelock 和执行，并可由交易 ID 审计。
- 执行型提案在签名前展示 ABI 解码后的实际动作与资产变化。
- 索引数据与链上数据不一致时，以链上为准并明确提示。
